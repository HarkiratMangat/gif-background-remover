# GIF Background Remover

## What this is
A skill + script for removing/making transparent the background of animated GIFs (icon/sticker/ emoji art, usually antialiased vector art, sometimes pixel art) while protecting interior design elements, plus optional file-size optimization for platform limits (e.g. Discord's 256KB sticker cap). Built and maintained by Harkirat, the sole user. The skill is also uploaded standalone to claude.ai — this repo is the working copy where it actually gets developed and versioned.

**Before doing anything else this session, read `~/.claude/projects/-Applications-Claude-Code-Gif-Background-Remover/memory/user_working_agreement.md`** (start of that folder's `MEMORY.md` index) — it's the living summary of how Harkirat works and what this project expects, with links to every other memory file. `SKILL.md` is the deepest source of truth for the skill's actual operating instructions; `references/lessons.md` holds the full bug-postmortem/tool-evaluation history behind those instructions; this memory folder is the collaboration layer on top of both.

## THE END GOAL — full autonomy (Harkirat, stated 2026-08-17, reiterated the same day)
> "the end goal of this skill is to be completely automatically run-able, with it doing the analysis and recommendation itself correctly. So these edge cases and minor edits/fixes are essentially training and improvement meant to help it reach that completely autonomous phase. As such these fixes need to be considered and implemented properly into the skill's script so it can genuinely catch them and not repeat them. we need it to learn these mishaps, improve it, and stop them from happening again. We can't be manually force-tweaking things to get the correct output when edge cases like this happen. the manual tweaks are essentially just a verification/investigation layer to figure out *how* the mishap occured and how to fix it in the skill"

**What this means in practice, and it changes what counts as "done":**
- A manual flag tweak that fixes an output is **not the fix** — it is the *investigation result*. The fix is whatever change to `--analyze`/`--recommend`/the script makes the tool reach that same answer by itself next time. Delivering the corrected file while leaving the skill unable to derive it is an unfinished job, not a completed one.
- **Never hand back a good output produced by flags the skill did not recommend without also closing the gap that made the override necessary** — or, if it genuinely cannot be closed this session, recording it in `gif-deferred-list.md`'s AUTONOMY BACKLOG with the measured evidence and a concrete next action. Silent overrides are how the same edge case gets rediscovered.
- A *warning* in `--recommend`'s evidence does not count as a fix on its own: an autonomous run takes the suggested flags verbatim, so a warning nobody reads changes nothing. Prefer a real discriminator; emit evidence in addition, never instead.
- When a check cannot be made reliable, it is better for it to say so than to return a confident wrong answer — an unverifiable check must report "unverified", never a vacuous pass (`references/lessons.md` §13, §16, §17).

### What a claude.ai live-skill session can and cannot see (corrected 2026-08-07)
**A claude.ai session runs in its own isolated Linux sandbox. It has no reach into this Mac at all — not to read, and not to write.** Earlier wording here got this wrong in both directions and sent at least one session looking for things that cannot exist; treat the boundary as absolute:

One physical line per paragraph, list item or quoted paragraph; the editor wraps for display. Adopted from Dior's Builds, whose reasoning applies here more strongly than there: measured 2026-08-17, **2,239 of 2,965 prose lines (75.5%) broke mid-sentence**, so `rg` could not match most multi-word phrases (Dior's Builds decided the same at 64.6%). After migration: 2-9%.

Reflow with that repo's script, `--check` before `--write`; its token-preservation invariant is what makes the migration trustworthy, and it passed on all 28 files with 0 failures:
```

```
**This applies to every `.md` in scope, including the memory folder** — those were hand-wrapped during the very session that ran the migration, which Harkirat caught.

⚠️ **IT ALSO APPLIES TO PROSE INSIDE FENCED BLOCKS — copy-paste prompts, handoff prompts, chat messages — and NOTHING GATES THAT.** `reflow-prose.mjs` passes fenced content through verbatim (`isFence`, line ~124), and it is right to: it cannot tell a block of shell commands, where a line break is semantic, from a block of prose meant to be pasted into a chat, where a line break is noise. Harkirat's correction, 2026-08-20: *"this is on you. this is on your compliance and memory."* Concretely: a starting prompt, a handoff prompt or any block of English inside a fence gets **one physical line per instruction or paragraph**, exactly like prose outside a fence. ### A synthetic fixture can silently BE the negative fixture *(added 2026-08-20, from the fade-ladder guard)*
The painted-fade falsifier in `scripts/harness/test_fade_ladder.py` had to reproduce a hand-picked colour ramp by offsetting each stage perpendicular to the background-to-colour ray. **Two versions were built, both looked correct, and both were quietly a second copy of the NEGATIVE fixture.** A CONSTANT offset puts every stage on one line parallel to that ray, so each stage is a clean blend of the previous one and the product's pass-1 blend rejection deletes it exactly as it deletes a flattened stage — the palette came back with 3 entries and no ladder. Alternating the sign per frame looks like the fix and is not, because `build_art_palette` samples every 8th frame, so every sampled frame shares a parity and the constant case returns unchanged. **A fixture whose defect is invisible at the sampling rate the product actually uses is not a fixture** — and the only thing that caught either version was printing the palette the product actually derived, rather than trusting that the construction implied it. Check a new fixture by running the product's own extractor over it and reading what comes out, before writing a single assertion about it.

It found **five defects, three severe, in ninety minutes** on a build that had just passed the 797-asset corpus score, an xhigh code review with ten finder angles, and a full PRE/POST render diff. ⚠️ **Those three regimes are blind in the same structural way** — the corpus measures CLASSIFICATION and every defect lived downstream of it; the code review reads CODE and `enclosure_ratio 0.825 looks incidental` is correct code producing wrong advice; the render diff catches REGRESSION and every defect was longstanding, so PRE and POST agreed. All three compare the product against itself or against a label, never against what a user wanted. Full write-up, method and caveats: `docs/investigations/2026-08-19-three-agent-package-trial.md`; the product half a live session needs is `references/lessons.md` §34.

⚠️ **And do not trust an output scorer you have not falsified.** The grader written for that trial reported hurricane **100% correct on all three agents** while human review called it a disaster on all three. Three separate causes, each worth avoiding by name: a **binary keep/remove ground truth cannot grade a FADE** (it wants progressive translucency, so the bug scored as perfect); it had **no edge-quality measure at all**, missing the outline artefacting a human noticed first on three of five assets; and it reported a **MEAN over sampled frames**, so a defect sitting on 16 consecutive frames read as 99.9% and vanished. **Report the worst frame, never the mean**, and before using any scorer to validate a fix, check it can fail on the defect that fix targets.

9. **Diff the RENDERED output, not just the recommendations.** `python3 scripts/harness/render_baseline.py --set fast --out <new>.json` (24 assets) for a routine check, `--set standard` (106) before a release, then `--compare <old>.json <new>.json`. **`--jobs` defaults to `machine.default_jobs()`, measured at call time — NOT a constant.** It used to be `min(8, cpu_count)`, which on this machine is wrong in both directions at once: `os.cpu_count()` reports 8 on an M1 Pro but only **6 are performance cores** (a unit scheduled onto an E-core becomes the run's long tail, and `analyze` is 21.0s user of 22.5s real, i.e. single-threaded and CPU-bound), and the constant ignored memory entirely while one `analyze` peaks at **488 MB RSS** on a 16 GB machine that has been observed with 0.8 GB free and 8.6 GB of swap in use. Past the point where the working set stops fitting, more workers make a run SLOWER and unpredictably so — the same 107-asset render set was measured at **976s and 488s on consecutive runs**. `default_jobs()` returns `min(performance_cores, available_memory / 500 MB)` and every run now LOGS which limit bound the answer. Run `python3 scripts/harness/machine.py` to see it. Earlier measurement, still valid: the fast set went 440s → 212s (2.2x, floored by a single 212s asset; the standard set has a much smaller tail). Threads, not processes, because every unit is a CLI subprocess. Proven equivalent before the default was changed: `--jobs 1` vs `--jobs 8` gives 46 vs 46 records, **0 changed**. Pass `--jobs 1` to force serial. **Every asset is rendered TWICE — native, and through `--resize-max-dim` at half its larger side under a ` [resize]` key — because `--auto` alone cannot express the most destructive thing a wrong `--pixel-art` verdict does, switching the resize filter from LANCZOS to nearest.** Added 2026-08-18 after the v5.5.0 hardness change moved 8 verdicts inside the render set and all 106 outputs came back byte-identical: every asset whose verdict moved was an already-transparent source whose render is scope-confined, so "0 changed" partly meant "this set cannot express the change". Measured separately: on the 29 undetected sprites the resize pass is worth 388-1,333 manufactured partial-alpha pixels each (`references/lessons.md` §29.10). Every asset goes through the real `--auto` CLI and its alpha plane is fingerprinted; the harness freezes a copy of the script under test at startup, because the mid-run-edit trap was hit twice in one evening and care is not a control. ⚠️ **Freezing is now `scripts/harness/snapshot.py::freeze()` and `run_populations.py` uses it too** — until 2026-08-20 only `render_baseline.py` froze, so a 12-minute analyze pass silently forbade editing the file it was measuring and nothing said so. The practical consequence is that **a long render or score pass no longer blocks editing**, which is the only way two population-scale measurements and a code change fit in one session. Freezing costs nothing: the snapshot is byte-identical, so the analyze cache's script-SHA key is unchanged and a frozen run shares its namespace with an unfrozen one — asserted by `test_freeze_keeps_the_analysis_cache_namespace`, not assumed. `candidates.py` is unaffected; it never invokes the script. **This gate exists because a correctness fix reached one of five code paths while every `analyze()`-level number said it had landed** — reading the code and measuring one function found four consumers, and only rendering found the fifth (`--auto`'s erosion auto-calibration, which left 38.7% of a sprite opaque, worse than the bug being fixed). The 2026-08-18 PRE/POST pair in `local/pixelart-probe/` is the worked example.
10. **Re-score the labelled populations through `analyze()` whenever an `edge_hardness` rule or threshold changes — or whenever anything a hardness rule READS changes.** ⚠️ The narrower trigger is not enough, measured 2026-08-18: the composited-frames change touched no rule and no threshold, and `all_rgb_frames[0]` turned out to feed `source_transparency_is_the_background`, whose result gates one of the band rules. **When the change can only reach part of the corpus, score that part rather than all 719** — the composite is a no-op on any source without partial alpha, so 38 partial-alpha assets (the 20 most translucent plus a spread) were the whole affected population and took four minutes against the full run's hour. A gate scoped to the population a change can reach is a better gate, not a weaker one; a gate scoped to the population you happen to have is the failure this list already records twice. `python3 scripts/harness/run_populations.py --out <new>.json` — **797 assets, ~7 minutes** (measured 2026-08-19: 413s at `--jobs 8` against 2,592s serial, 7.0x per asset; `--sample N` subsamples for iteration and prints a warning that its figures must not be quoted or gated on). **`--jobs` defaults to `machine.default_jobs()` here too, as it does in `candidates.py`** — a speed knob nobody remembers to pass is a gate that gets skipped instead of run. See the render-gate entry above for why a constant was wrong.

⚠️ **`analyze()` RESULTS ARE NOW CACHED, and this changes what a re-score costs.** `analyze()` is a pure function of (the asset's bytes, the script's code), so it is computed once per script version and served from `local/.analysis-cache/` after that. Measured 2026-08-20 on the `trial` population: **31.3s cold → 0.6s warm**, with all 8 records byte-identical across cold, warm and `--no-cache`. **The key is `analysis_fingerprint(script)` plus each asset's mtime and size.** ⚠️ **It used to be the SHA of the WHOLE script, so any edit invalidated every entry** — safe, and exactly why a session that edits the product paid cold cost over and over. Since 2026-08-21 the key is derived from the code `analyze()` can actually REACH: every module-level statement that is not a function definition (imports, constants, classes) plus every function transitively reachable from `analyze`, docstrings stripped. **34 of 108 module-level functions are in that closure.** Adopted from Dior's Builds' `utils/algoFingerprint.js`, and measured over this file's real history before adopting it — of the 28 commits that changed `remove_gif_background.py`, the old key invalidates on all 28 and this one on 19, so **9 (32.1%) now keep a warm cache**. ⚠️ **The naive half of that transfer was measured and REJECTED**: stripping comments and docstrings from the whole file survives only 1 of the 28 (3.6%), so comment density is not where the cost is. Every uncertain case — an unparseable file, a missing root, any exception — falls back to the whole-file SHA, because a false invalidation costs one re-analysis and a MISSED one serves the pre-change answer to the change's own gate. A real fingerprint is prefixed `a` and a fallback is not, so `stats()` shows when a run silently fell back. It cannot see dispatch the AST does not name (`getattr(mod, name)()`, a dict of callables); none exists today, and adding one on a path `analyze()` reaches means extending `ANALYSIS_ROOTS` or dropping back to `script_sha`. Twelve falsifiers in `scripts/harness/test_analysis_fingerprint.py`, each PAIRED so neither half passes vacuously. `--no-cache` forces recomputation; ten falsifiers in `scripts/harness/test_harness_infra.py` cover script-change, asset-touch, corrupt-entry and disabled paths, plus a round-trip of a REAL `analyze()` result (it returns numpy scalars, and a naive `default=str` would write a float64 as its repr and read it back as a string while reporting a hit). It exists because one session on 2026-08-20 ran full analyze passes over overlapping populations **six separate times**, one of them recomputing another's discarded answer over 105 assets at ~22s each. Every default was proven equivalent to serial on the labelled population first: 31 vs 31 records, 0 differing, for both scripts (`candidates.py` 39s → 11s, `run_populations.py` 272s → 79s on that set) — and report recall AND specificity **per population**, and for sprites **per pack**. A pooled figure over a lopsided population is a statement about its largest member: an 86.4% sprite recall stood for a day before the per-pack split showed it was really Tiny Swords (409 of 493 files) while two packs sat at 0.147 and 0.250.
