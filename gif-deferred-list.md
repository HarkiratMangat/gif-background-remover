### `[P1 · L (first slice: M) · Opus5-High]` A 40-frame spread cannot see a transient, and the trigger for looking harder cannot be computed from the spread *(filed 2026-08-20, Harkirat's question)*

`analyze(max_samples=40)` samples the expensive per-frame work — the candidate-region enclosure search, edge hardness, the band-interior/fade detection. Several checks already scan every frame (tumble margin, the small-region histogram, the blank-frame scan added 2026-08-20), so this is about the sampled half only.

**The failure is a RATIO, not a class of asset: a transient of length L in an N-frame file is invisible when `40/N < 1/L`.** Measured 2026-08-20 — `for-you.gif` (144 frames) loses its navy outline for **37 consecutive frames** and a 40-sample spread lands ~10 samples inside it, so it was caught; `in-love.gif` (48 frames) has fade stages living 1–2 frames each and 40-of-48 samples nearly everything; but the changing-background asset filed the same morning has a 5-frame window in 30, and a 10-sample scan read **78.6% at frame 10 while frame 12 was 0.0%**. The same content at 300 frames misses all three.

⚠️ **So a "this asset looks hard" trigger computed FROM the 40 samples is unfalsifiable in the direction that matters** — the assets needing escalation most are exactly the ones whose difficulty is invisible at 40 samples. Do not build that.

**Do: make the CHEAP pass dense and let it nominate frames for the EXPENSIVE pass.** The blank-frame scan is the worked example — every frame, no measurable cost, because what makes `analyze` slow is the enclosure search, not decoding. One extra cheap pass over every frame collecting the detected background colour, the pixel count of each provisional palette colour, and the non-background pixel count yields four nominations, **three of which are defects already filed here and currently undetected**:
1. **background colour MOVES** beyond tolerance → the changing-colour-background item above.
2. **a colour that carried the outline COLLAPSES** on a run of frames → `for-you.gif`; today it survives only because `--recommend` happened to pick a colour present in all 144 frames.
3. **a colour appears in very FEW frames at LARGE pixel counts** → `in-love.gif`'s fade stages; this is the fade-ladder signature from `references/lessons.md` §34.2.
4. **non-background count hits ZERO** → the blank frame. Already shipped.

Each yields FRAME INDICES, so escalation adds a handful of frames to the spread instead of raising 40 → N.

✅ **FIRST SLICE DONE 2026-08-21 (Part 2).** `nominate_sample_frames` reads the dense scan's own summary and names frames; `sample_idxs` unions them in, capped at 8 and thinned across the span. **Cost measured, not assumed:** the dense pass is a median **3ms** across 910 assets, max **0.62s** on the longest (a 250-frame asset) — and it reuses the loop and mask `analyze` already ran, so nomination itself adds nothing.

⚠️ **THE MOTIVATING ASSET CANNOT EXERCISE IT, and that is a finding rather than a failure.** `Pew Pew Pew.gif` is 30 frames — under `max_samples=40` — so every frame is already sampled and there is no gap to close. Forced to a 10-sample spread it nominates frames 11, 12, 13 and 15 and **recovers 3 the spread had missed**, which is the mechanism working; at the shipped setting it is simply not a case. The real production case is `Pixel Saber.gif`: **213 frames, two 3-frame transients (58-60, 153-155)**, where 40/213 = 0.188 against 1/3 = 0.333 — exactly the ratio failure this item describes. It gains 5 frames. **Scoped by measurement rather than assumed:** the dense pass was run over ALL ten populations (910 assets) and exactly **1** gains frames at `max_samples=40`, so the affected population is one asset plus the eight the crash fix recovers.

⚠️ **TWO GUARDS, both added because a real asset walked straight through the naive rule.** (1) `recolored_frame_indexes` is populated from the raw per-frame comparison **even when the verdict is `null`** — measured on an asset reporting `changes: null` ("there is no background colour for the animation to change") with 44 of 60 frames listed as recoloured. Nominating off that escalates the expensive pass on a question the summary already called not applicable. (2) The same for an already-background-removed source, delivered through a cheap dense-loop hint because the authoritative flag reads `sample_idxs` and cannot be consulted before it exists. Without either guard, 3 assets nominated instead of 1.

✅ **AND IT UNCOVERED A PRE-EXISTING CRASH, unrelated to this work but found by it.** `summarise_background_color_stability` bails only when FEWER than half the frames have a readable background corner; anything in the 50-100% band reached `None > int` and raised a bare `TypeError` with no file name and no frame number. **3 real corpus assets crashed `--analyze` this way**, silently, and now analyze. ⚠️ This first read **8**, taken from the render harness's `no_output` list — a DIFFERENT failure mode (no output FILE from a render), conflated with an analyze crash. Re-running each against the pre-fix script showed only 3 were this bug; the other 5 analyzed fine before and after, so their `no_output` has another cause and is still open. **Two failure lists that overlap are not the same list.** Same class as §39. 12 falsifiers in `scripts/harness/test_frame_nomination.py`, including the exact 50-100%-readable shape and a check that the fix did not buy its silence by disabling the rule.

### `[P3 · S · Sonnet5-High]` `CatPackFree` sits at 0.250 (1/4) — four assets *(filed 2026-08-19)*

### `[P2 · M · Opus5-High]` Re-analysing ANY GIF this tool writes classifies antialiased art as pixel art — 8.3% with no compression at all *(filed 2026-08-18; retitled twice the same day as the sample grew 3 → 14 → 48)*

**Added 2026-08-18 by the v5.5.0 audit pass, asking what a new measure does to the tool's OWN output.** `--compress heavy` quantizes colours, and quantization gives a 1px antialiasing ramp flat neighbours it did not have — so `plateau_cliff_ratio`'s founding premise ("a 1px ramp cannot be a cliff, because the ramp pixel is a plateau of length 1 by construction") is a property of the FILE, not of the artwork. Measured, source → its own `--compress heavy` output: `gem.gif` 305 colours/not-hard-edged → 122/**hard-edged** (cliff 0.324); `heart_ORIGINAL.gif` 320/not-hard-edged → 108/**hard-edged** (cliff 0.343); `add.png` unchanged. Two of three flip. Reachable in an ordinary workflow — compress for a size limit, then run the tool again on the output — and it is the likeliest explanation of the two false positives that survive in the corpus, both already-processed cutouts caught by the cliff ratio.

**The obvious veto was measured and rejected, so do not re-derive it.** Over the 451 assets the cliff rule detects correctly, colour count is median 12 / p95 20 but reaches 50, 56, 98, 123, 172, 221, 242 and 1,233 — dithered and photographic pixel art is exactly what that rule exists to reach. A veto at >100 (needed to catch the 108/122 cases) removes **0 of 2** corpus false positives and costs 5 real detections; at >80 it removes 1 of 2 and costs 6. Not implemented.

⚠️ **2026-08-18 — MEASURED ON 48 ASSETS, and both this item's original title and its first correction were wrong.** Every asset run through the real CLI at all four tiers and re-analysed: **`none` (no compression, the control) flips 4/48 = 8.3%**, `optimize` **12/48 = 25.0%**, `medium` 10/48 = 20.8%, `heavy` 6/48 = 12.5%. **14 of 48 (29.2%) flip at some tier, and `heavy` is the LEAST affected.** Nearly every flip is `plateau_cliff_ratio` clearing 0.30 (0.303–0.573 over 2,150–16,104 steps).

**The control IS the finding: `--compress` is not required.** Writing a GIF is itself a palette reduction — `add.png` goes 402 composited colours to 133 with no compression flag — so the hazard belongs to the container, not to a tier. **The rule is: decide content type from the ORIGINAL asset, never from any file this tool has written.** ⚠️ Note the sampling failure worth carrying: a 14-asset PREFIX of an evenly-spread sample said the control flipped 0, which is how the previous correction got written. A prefix of a spread is not a spread. **Do:** the size of the class is now known; what remains is deciding between a real discriminator for quantization-induced cliffs (a dither signature is the obvious candidate — gifsicle's colour reduction leaves one and hand-drawn pixel art does not) and documenting it as a hard limit in SKILL.md's content-type section.

📏 **2026-08-18 — the class is also measured on 118 assets from the opposite direction, and the item stays OPEN because measuring it is not fixing it.** Real antialiased emoji downscaled to 64px and quantized to a small palette — which is what any lossy small-icon export IS — reach pixel art's numbers: at 32 colours 11.0% clear a palette-mass threshold the Orc sprites sit inside, at 16 colours 30.5%. **That reaches the 16-colour floor already in the released code too, not just the cliff ratio**, so this is a general property of quantization rather than a quirk of one measure (§29.12). **Do:** build a small corpus of the tool's own outputs at each `--compress` tier and score them, so the size of the class is known rather than guessed (3 assets is not a population).
