# Skill version history

**v6.2.0 is still PENDING as of 2026-08-24** — not yet minted, since it hasn't merged. ## v6.1.1 — full entry

**v6.1.1** was a *correction* bump: two packaged files pointed at things the sandbox cannot open, and the gate meant to catch that could not see either of them.
- **A pointer a live session cannot follow is a broken instruction, and two shipped in the v6.1.0 package.** One was a function docstring citing an investigation document that exists only in the development repo; the other named two corpus files from a gitignored asset folder. Both were found by gating the BUILT ARTIFACT rather than the working tree, which is the only place "tracked but not packaged" is visible. The provenance prose stays — a reader still learns where a number came from; only the unreachable paths are gone.
- **The gate was blind in two ways, and both are now closed.** It scanned only **backticked** tokens — so a PYTHON DOCSTRING, which uses no backticks, was invisible to it, in the one file a live session reads most closely. And it tested `os.path.exists()`, so a path that does not resolve from the repo root fell through every branch: a pointer is unreachable whether or not this machine happens to resolve it. Both defects are proven red-green — reintroducing either makes the repo's documentation gate exit 1 — and the strengthened gate immediately found a third pointer on a line that had just been hand-edited.

## v6.1.0 — full entry

**v6.1.0** was a *minor* bump: two new capabilities, eight defects of one shape, and two new `--auto` refusals.
- **`--unprotect-region` — a region-scoped BACKGROUND removal that keeps the artwork.** Until now nothing could say *"this enclosed interior IS the background"*: `--protect-outline-color`, the fade path's topological protection and the band-interior scan all independently classify an enclosed region of background colour as intentional design. Measured on a broadcast-tower asset, the first two left the **same 8,569 enclosed near-white opaque px with the same bounding boxes** — two mechanisms, opposite routes, identical verdict. `--remove-region`, the obvious workaround, force-deletes its whole box and took **73% of the artwork** with the white (navy 23,157 → 6,297). `--unprotect-region` re-keys only background-coloured pixels inside its box: **8,569 → 0 with the artwork at 23,478 and the fade intact**. It is applied downstream of the fade render path, so it is the **only region flag that composes with `--recover-fade-alpha`** — "recover the flattened fade AND remove the interior white" is one command rather than a choice. `references/lessons.md` §43
- **Its boundary is keyed by COLOUR and softened by GEOMETRY, because either alone is visibly wrong.** A hard threshold at `--tolerance` left the antialiasing ramp opaque — 236-454 px per frame with the count moving every frame, so the rim flickered. Replacing it with the main path's colour ramp fixed that and made a worse defect: a pixel just outside `--tolerance` gets an alpha near 1, so **12.4% of a fixed 2,060 px ring came out fully opaque and pale**. Combining the ramp with `apply_remove_regions`' geometric taper gives **0.5%**. ⚠️ A temporal-stabilisation variant was built and REJECTED on measurement — the ring's lag-1 class-flip rate is 0.062, i.e. smooth animation, not dither noise. §43
- **`--recommend` OFFERS it, and never applies it.** Any region whose outline does not enclose it on every frame gets a second note naming `--unprotect-region rect:x,y,w,h`. Whether an enclosed interior is design or background is a statement about intent, not something the pixels answer. A region enclosed on **every** frame gets no hint — a hint that fires on every asset is noise. ⚠️ The box is the region's extent on the SAMPLED frame and is labelled a starting point: rendered with it, an interior that grows across the animation left **2,340 px of residue**, and a 15% padding heuristic cleared that at a cost of **1,287 px of artwork** by reaching the outer silhouette. §43
- **A ~1px pale ring on EVERY WebP/AVIF/APNG the manual path had ever produced — the only defect a person noticed unprompted, and `--verify` called it clean.** `--edge-cleanup-erosion` defaulted to a flat **0** on those formats, on the reasoning that partial alpha already represents the antialiased edge; `edge_fringe_check` returned `looks_fringed: false` on it. Measured on one asset, erosion 0 against erosion 1, counting edge pixels that kept the BACKGROUND's tint rather than the art's: worst frame **852 → 1**, total **92,560 → 10**. `--auto` never had the defect because it calibrates against the asset's own fringe curve, so the manual path now runs that same calibration rather than taking a new constant — the level is a property of the asset, and a fixed level set too high eats thin strokes. It stays selective: one asset calibrates 0 → 1, another stays at 0, a recovered fade stays at 0. §44.1
- **Three flags that were accepted and silently discarded now say so.** `--webp-quality` is read only on the lossy branch, so q70 and q45 produced **byte-identical** output on the default path — it warns and names `--webp-lossy`. `--fade-color` is read only inside `--recover-fade-alpha`, so alone it did nothing at all (measured: the faint fade stages came out **0.0% opaque, mean alpha 0.000** — removed outright, not "left opaque" as first reported) — it is now a hard error naming the pair. And `--target-kb`'s fit reported the dimensions from BEFORE it ran, so a session reported **482×513 for a file that was 120×128**; every fit-completion line now reads the dimensions back off the written file. §44.2, §44.3, §44.6
- **`--verify` no longer returns the shape of success without checking a pixel.** It skips every pixel check when the output canvas differs from the source, so every `--crop`ped deliverable verified vacuously — four runs in a row returned in 0.9–2.0s having checked nothing. The report now carries `checks_skipped` and `verified`, with `verified` DERIVED from the skip list so a pass cannot be manufactured by a check quietly declining to run. §44.4
- **`--min-width` / `--min-height` / `--min-dimension`: a byte cap may no longer outrank a stated resolution.** The fit walked down the scale axis and delivered 120×128 against an explicit "at least 128px wide". These remove only the breaching scale rungs, so quality and frames are still traded, and the failure message names the floor. A bare `--min-dimension` constrains the **shorter side** — a 600×100 asset passes `--min-width 128` and fails `--min-dimension 128`. The fit also **prints a cost estimate before it starts**: one 144-frame asset took 207.84s, and a first attempt died at a 120s tool timeout having produced nothing. §44.5
- **`--auto` now ASKS rather than guessing, on two decisions it had no basis for — and both questions arrive in one refusal.** A coin-flip enclosure (it protected sparkle interiors a user had asked to have removed, and reported success) and a fade it can NAME but not classify (§41's 91 assets do not separate, so auto-applying stays refused — the defect was the delivery channel). ⚠️ **The autonomy tension is not smoothed over:** `--assume-protect`, `--assume-remove` and `--assume-no-fade` answer both in advance, a run that acted on an assumption says so, and the **measured refusal rate is 12.8% across 304 assets** (emoji 19.7%, small icons 7.0%) — a minority, not everything. §44.7
- **The batch summary flags an output another format beats on every axis, and `--recommend` no longer suggests a pair the renderer refuses to honour.** An AVIF beat its sibling WebP on resolution, frames AND size at once while the tool printed `2/2 succeeded.` and ranked neither; only strict domination is reported, so a genuine tradeoff is left to the user. And `--protect-outline-color X --recover-fade-alpha` was being recommended although the fade path ignores every protection flag — the exclusivity is declared once and read by both sides now, protection wins, and the recommendation says what it gave up. §44.8, §44.9
- **The first executable instruction in this file used to fail silently off this machine.** The navigation recipe was `rg`-only, and `rg` is absent from the claude.ai sandbox; a session substituting `grep` got **zero matches and exit 0**, because `#{2,3}` is ERE and plain `grep` is BRE. It is now `grep -n "^##"`, a literal string that behaves identically under `grep`, `grep -E` and `rg`.

⚠️ **v6.0.0 is PUBLISHED, and its notes cover everything since v5.4.0 — v5.5.0 was built but never published, and its entry is folded into this one's history (`references/version-history.md`).** The two defects that held it back are both closed: a fade that popped instead of ramping (§34.2 — the flag is now DECLINED on a painted fade, `fade_coherence` 0.688 → 0.998) and a GIF path that could silently truncate (§34.1 — the render now REFUSES instead of writing the truncated file). One known limit is deliberately still open and is now loud rather than silent: `--recover-fade-alpha` takes its own render path and ignores every protection flag, printing a warning that names them (§34.4). **v6.0.0** is a *major* bump: two data-loss classes on the alpha path, a reversal of a compression default, a seventh pixel-art discriminator, a new region flag, and the ground truth the detection figures rest on rebuilt by eye. Detection over the independent populations goes **recall 0.8932 → 0.9644**.
- **One invocation now takes N files.** `--analyze`/`--recommend` read every path given and return a JSON list; rendering takes three or more bare paths as three or more inputs, and `--out-dir DIR` makes even two paths two inputs, deriving each output name. The 2026-08-19 trial measured **50-74 tool calls for a five-asset job** because the CLI had no way to say "these five files" without hand-building a manifest first. Per-run boilerplate is emitted once per PROCESS, so this also stops the container ranking being re-read once per file. See "One invocation per JOB, not per FILE".
- **A stated size/format gate, so a target is never guessed.** No requirement stated -> full resolution, no compression flags. A real constraint -> act on it. Anything that would need a guess -> ask. See "The size/format gate"; the trial measured variant sprawl rising as the user's constraint got vaguer.
- **`--target-kb` on WebP/AVIF/APNG is a concurrent 120-rung grid, and a deep downscale now ranks BELOW frame-stride.** Measured on 640px flat vector art: downscaling to 75% made the file **2.3x LARGER** and stayed larger at 50% and 37.5%, while frame-stride 2 at full resolution beat all of them. Five of seven realistic byte targets now deliver **full resolution** where they used to deliver 160-240px. Worker count is probed, never assumed, and falls back to serial wherever it cannot be probed. `references/lessons.md` §42
- **`--recommend` no longer prints the word "verified" over a number that says otherwise.** `Region 1: outline c83c78 verified across 144 frames (68% enclosed)` — an autonomous run acts on flags, but a human auditing one reads the word. Measured over **269 verified-outline regions across five populations before any band edge was picked**: 168 (62.5%) sit at exactly 1.000, 6 at exactly 0.000, and **95 — 35% — lie between, every one of which printed "verified"**. Three bands now: at 1.000 *verified on all N frames*; between, *a COIN FLIP, not verified*, with what to check named; at 0.000, *a closed shape on the sampled frame that NEVER encloses this region* — the recommendation still stands (rocket and satellite reach 0.999/1.0 protected coverage) but says so. The `0% enclosed` contradiction was two different fields read as one claim. A region that misses the intentional-design bars *narrowly* now reads as unsure rather than as a decision. `references/lessons.md` §38
- **An animation whose background CHANGES COLOUR mid-way is now detected, reported and refused.** `--bg-color` is one value and detection reads one frame, so every frame after the recolour keyed against a colour no longer on the canvas and kept its whole background as opaque artwork — while the file wrote, had plenty of opaque pixels and passed every quality check the tool has. Measured on a 30-frame asset running magenta → green across frames 11-15: the frame-0 colour covers **2.37% of frame 0 and 0.00% of frame 12**. A frame counts as recoloured only when its corner-majority colour moves >40 units AND the reference colour's coverage collapses below 15% of its frame-0 share — **each half alone has a measured false positive** in the 65-asset animated control. Scored on **148 assets across three populations**: **6 of 6 positives fire, 0 of 142 negatives do**, and the verdict is tri-state so an unmeasurable case reports `null`, never a quiet pass. ⚠️ The third population — 37 already-background-removed assets — was added after a PRE/POST render diff caught the refusal firing on **9 of them**, all false positives, on a class the original 71-asset control could not contain. `--allow-changing-background` is the escape hatch. `references/lessons.md` §36
- **`--recover-fade-alpha` is now CONFIRMED before it is recommended, and refused when there is nothing to recover.** The recommendation keyed on a cheap screen (a band-interior region whose colour distance from the background moves across frames); the renderer keys on the fade detector over the art palette. Measured across the 34 assets where the flag was being emitted, the two **disagree on 16**, and that half holds every catastrophic output: worst `bg_removed_worst` **0.0000** — 86.4% of true-background pixels alive at alpha 1-9, a translucent ghost of the whole frame. The screen is kept and now confirmed by the detector, reported as three states whose fall-through is *unverified*, never a pass. Worst three go **0.0000 → 0.5043**, **0.0004 → 0.7241**, **0.1759 → 0.9176**; one asset that exited 1 now renders at 0.9945; **all 17 confirmed-fade assets are byte-identical** and 9 of 10 white controls unchanged with the tenth improved. Forcing the flag with nothing fading now refuses instead of writing a ghost. `references/lessons.md` §35
- **Edge-cleanup erosion is auto-calibrated to 1px unless the asset's own curve EARNS a second, and the reason is 448 renders rather than a threshold.** The calibrator picks the smallest erosion whose outer-ring fringe fraction stops improving — a sound rule about the thing it measures, with **no term at all for what erosion costs**. On art that ramps into the background (a glow, a soft outline, antialiasing baked into an opaque GIF) the curve keeps falling as erosion walks inward through the artwork, so the "floor" is simply wherever the candidate list stopped. Two cost terms were built for this and both failed their own acceptance. What settled it was rendering **112 assets at erosion 0, 1, 2 AND 3 through the real CLI** and reading the answer: **no asset anywhere lost less artwork at a higher level — 0 of the 104 that scored at all four levels, at zero margin**; going above 1 improved background removal by **at most 0.021** (10 assets, 6 of which never escalated); going from 0 to 1 buys up to **+0.622**. So erosion earns its place exactly once. PRE/POST on 186 assets: 37 move, the erosion-caused population is **better on 28 and worse on 0** (median 0.614 perimeter rings of artwork recovered, max 2.079), `art_kept_worst` never falls, and the 54 controls are worse on **none** of the four measures. ⚠️ The ceiling is ONE function read by BOTH consumers — `--auto`'s post-render correction escalates on its own and a previous fix left it climbing straight back into the level calibration had just rejected. ⚠️ **This bullet used to read "can no longer be auto-calibrated above 1px", and that is no longer the whole rule.** Level 2 is reachable, but only for an asset whose own fringe curve is CONVEX at 2 — the second pixel removing MORE than the first did, which is what a genuinely two-pixel-thick fringe looks like and what the metric walking inward through artwork never does. Plus one guard: the extra step is earned only from level 1, so 0 → 2 is unreachable. Measured on 336 assets: 114 produce a full curve, 8 show a knee, and **3 promote — 2.6% of the assets whose calibration runs, 0.9% of the corpus**. `references/lessons.md` §37, §37.10
- **A cheap pass over EVERY frame now nominates frames for the expensive 40-frame spread.** `analyze` samples the costly per-frame work (enclosure search, edge hardness, fade detection) at up to 40 frames, so a transient of length L in an N-frame file is invisible whenever `40/N < 1/L`. ⚠️ **A "this asset looks hard, sample more" trigger computed from those same 40 samples cannot work** — the assets needing escalation most are exactly the ones whose difficulty is invisible at the rate the trigger would read. So the pass that already runs on every frame does the nominating instead, and the expensive pass adds the named frames: a background colour that moves beyond tolerance, and the frame where the reference background plane is smallest. Measured over **910 assets**: the dense pass costs a median **3ms** (max 0.62s on the longest, a 250-frame asset), and exactly **1 asset** gains frames at the shipped setting — a 213-frame file with two 3-frame transients that a 40-sample spread steps over. Capped at 8 added frames and thinned across the span, because a long recolour is one event whose middle matters as much as its start. Two guards, both added after a real asset walked through the naive rule: an UNVERIFIED verdict nominates nothing (the recoloured-frame list is populated even when the verdict is `null`), and neither does an already-background-removed source. `references/lessons.md` §40
- **`--analyze` no longer dies with a bare `TypeError` when some frames have a transparent background corner.** The background-stability scan bails only when FEWER than half the frames are readable; anything in the 50-100% band reached a `None > int` comparison and raised, with no file name and no frame number — the same class §39 fixed for a different cause. Measured: **3 real corpus assets** crashed this way, every one of them silently. ⚠️ An earlier draft of this bullet said 8, taking the count from the render harness's `no_output` list — that is a DIFFERENT failure (a render produced no file) and only 3 of those 8 were this crash; checking each against the pre-fix script is what separated them. An unreadable frame is now counted and reported rather than compared, and a partial scan says so instead of reading as a clean bill of health.
- **A soft glow on a dark background now gets its colour NAMED instead of a false "nothing to recover".** The fade gate asks whether a colour is *almost never solid*; a glow's colour is necessarily both its bright core and its falloff, so it misses by **0.00023** — about two pixels in 9,558 — and the falloff is removed as background. Naming the colour works (`--fade-color`, measured: partial alpha **287,651 → 779,583**, `edge_cleanliness` 0.0000 → 0.4656). ⚠️ **Deriving it automatically was built and FALSIFIED against the 91 assets in the same branch** — the population §35 measured as catastrophic to recover — where the glow ranks 11th on faint-pixel mass and interleaves with the documented disasters on every axis. So `--recommend` now computes the candidate, says plainly that the falloff will be cut, and hands over the exact `--fade-color` value; it does not apply it. `references/lessons.md` §41
- **A small or thin KEPT art component is now exempt from edge-cleanup erosion, which is the mirror of a mechanism that only ever existed one way round.** `--erosion-exempt-max-size` protects a small REMOVED region from being *inflated* by erosion (§11); nothing protected a small OPAQUE component from being *erased* by it, so a 2px-wide crescent rim is taken to zero by the uniform 1px trim that is proportionally nothing on the silhouette beside it. `check_erosion_damage` had measured exactly this since v5.0.0 and was **print-only** — an autonomous run takes flags verbatim and reads no stderr, so a warning nobody acts on changed nothing. The fix acts on that diagnostic's own rule (components ≥25px cut below 30% survival) and restores their exact pre-erosion pixels, **at whatever level was already chosen** — so it reaches the assets no level policy can, and it runs on EVERY frame rather than the diagnostic's 40-frame sample, because a protection applied on only the sampled frames converts a uniform loss into a flicker. Measured on the 42-asset erosion-residue population through the real CLI: the warning goes **20 → 0**, `art_kept_worst` is better on **19 of 20 and worse on 0** (max +0.1769), the calibrated level moves on **none of the 42**, and the 22 clean controls are **score-identical**. Cost: `bg_removed_worst` worse on 8, worst **−0.0026**. `--no-erosion-component-protection` turns it off. `references/lessons.md` §37.9
- **A fade the artist PAINTED is now told apart from one the export FLATTENED, and `--recover-fade-alpha` is declined for the first.** The flag reconstructs alpha from how pale a pixel is — right for a translucent element a GIF export flattened, wrong for a solid pale shape drawn getting lighter, which it makes see-through. The discriminator needs no threshold: a flattened fade is `bg*(1-a)+c*a` **by construction**, so its stages lie exactly on the background-to-colour line and the palette's blend rejection deletes them — **one** detected fading colour. A painted fade carries hue drift, survives, and shows up as a LADDER of near-collinear colours. Measured: `crystal`, `gift`, `love` and `heart` — the four assets this flag exists for — report **1 fading colour and 0 ladder rungs each**; `hurricane.gif`, the filed cliff defect, reports **8 and a 5-rung ladder at cosine 0.968**. Declining the flag there scores better on every axis, not just the one it targets: `fade_coherence` **0.688 → 0.962-0.998**, `bg_removed_worst` **0.3902 → 1.0000** (the "glitchy fade" was also keeping 61% of the background as a translucent ghost), `edge_cleanliness` **0.0000 → 0.9262-1.0000**. Three call sites, one implementation — `analyze()` reports it, `--recommend` declines and stops calling the format `webp-or-avif`, and the renderer refuses outright. `--fade-color` still bypasses detection entirely. **And the same gate's UNVERIFIED arm was emitting the flag**: `fade_colors_confirmed` is tri-state and documented "unverified, never a pass", but the gate tested only `is False`, so a confirmation step that raised fell through to the destructive branch on no evidence. Unverified now declines, and the format says GIF is *not disqualified* rather than *acceptable*. `references/lessons.md` §34.2, §38.1
- **A source's partial alpha was being promoted to fully opaque, and 218 of 249 corpus assets carrying a fade lost it.** `process()` built its working frames with a bare `convert('RGB')`, so a pixel the source drew at 35% opacity became byte-identical to a solid one and `estimate_alpha_and_defringe` re-derived its alpha from RGB alone. `love_emoji_128.webp` went in with 913 partial-alpha pixels and out with **0**, its 5,509 opaque becoming 6,422. Fixed with a MINIMUM, never an assignment — the colour path may still make a pixel more transparent, it may never invent opacity the source did not have. **207 of 249 now keep 90%+ of their partial alpha.** The control that had to run first: `--pixel-art` implies `--no-feather`, which is binary by design, and 20 of the 45 largest cases were that — without the split the headline would have been half artefact. `references/lessons.md` §31
- **The removal decision now keys on the COMPOSITE, and the output still carries raw art colours.** `analyze()` has composited partial-alpha frames since §28.5; `process()` had not, so the flags were chosen from one image and `color_mask` acted on another — 41 of 338 partial-alpha sources disagreed at the real removal reach, worst 18.41% of a frame. `compute_alpha_mask` and `estimate_alpha_and_defringe` take `rgb_key`; every colour COMPARISON reads it, every returned pixel still comes from the raw plane. 47 assets change, **opaque counts identical on every one**, and of the 5,166 partial-alpha pixels removed **65.0% are under 2% opaque and 0.0% are above half opacity**. §31.2
- **A seventh discriminator: a transition band that is REAL but narrow.** The vacuity gate silences both band rules on a hard-alpha cutout whose transparency is its background — correct for an EMPTY band, and it was applied to every such source. Among the 378 assets it silences: at ratio 0.000, 46 pixel art / 40 antialiased; at 0 < ratio < 0.20, **49 / 9**. Native-resolution pixel art carries a thin band (the artist's own 1px shading); antialiasing carries a wide one. `Tiny RPG Character Asset Pack` goes **0.235 → 0.941**. `plateau_cliff_ratio` could never have reached it: it needs flat runs of 2px, and 1:1 art has none by construction. §32.7
- **`--dither=floyd-steinberg` is REMOVED from `--compress medium` and `heavy`.** Measured on 23 gradient assets and, as a falsifier, 5 flat animated vector sources: it cost **11–24% file size, 8–12% colour error and 2.6–5x static-region instability** to buy a ~6% banding improvement. The falsifier did not save it — flat art improves too. Temporal crawl is the decisive axis and the precedent was already here: error diffusion is refused for ALPHA on exactly that ground. `--auto` is unaffected; `love.gif` is still `2fd526b6fb3b191c`. §30.1
- **`--remove-region-track` follows a moving hole.** The one case filed with no answer: a hole that must be punched while same-coloured decoration is kept, where neither differs in size or aspect and both move. The seed supplies what no single frame can — two identical holes are indistinguishable within a frame and completely distinguishable across an animation, because only one is where the seeded one just was. On an asset built to make that premise true: static `--remove-region` punches the target on **1 of 24** frames, the tracker on **24 of 24 and the decoy on 0**. Losing the target is reported, never hidden. §33
- **The ground truth was rebuilt by eye, and one apparent collapse turned out to be an artefact.** 267 assets had arrived labelled `antialiased` in a single pass with 8 inspected. Every disagreement was rendered to a nearest-neighbour contact sheet and judged: 9 were real pixel art, 7 are undecidable at 32–128px and are now `ambiguous` rather than guessed. `small_aa` specificity **0.887 → 0.970**. The `small_aa_quantized` specificity of 0.615 is NOT 45 false positives — it is the quantization hazard measured at scale, and checking ORIGINALS showed the whole Blox-Fruits family is smooth rendering in the source and blocks only in its 16-colour twin. §32
- **The 16-colour floor was tested against real negatives at last and DOES NOT MOVE.** Lowering it 16 → 12 looks like 4 detections for 20 false positives — until you notice all 20 removed false positives are in the DERIVED population. On the independent populations specificity is **0.9787 at floor 16, 14, 12 and 10 alike**. The measurement that would have justified the change was run and came out the other way. §32.5
- **Also:** the outline leak gate tests the union of border-touching background components instead of the largest (which can be an interior region of the artwork); `--translucent-region` warns when it touches zero pixels instead of silently no-opping; erosion auto-calibration is skipped on any source carrying its own partial alpha, after it read a restored ramp as fringe and shaved 6,844 pixels; APNG playback is confirmed by Chrome's own decoder (12 animated, pixel-distinct frames against a control GIF at 35); and a detector for "this file is our own output" was built, measured and falsified. §30.3, §31.1, §33.1

**v5.5.0** was a *minor* bump: a fifth pixel-art discriminator that finally reaches dithered and photographic art, plus three defects it exposed in the measures that were already there — two of which were recommending `--pixel-art` for ordinary antialiased vector icons — and a crash on static JPEG input.
- **`plateau_cliff_ratio`: of the STRONG colour steps in a frame, what share sit between two flat runs of 2px or more.** Upscaled pixel art transitions block-to-block; a 1px antialiasing ramp cannot, because the ramp pixel is a plateau of length 1 by construction. This is the measure that reaches the dithered and photographic assets that saturate `change_line_density`, and the fifth structural discriminator attempted — the four before it (modal run length, integer-lattice fit, duplicate-line density, gap regularity) all measured uniformity *unconditionally*, which is why a flat-fill vector icon scored like a pixel grid and killed each of them. **The repair was conditioning, not a new feature family:** uniformity is only counted at a real edge, so a flat interior contributes nothing. Scored against BOTH populations per §23.8's rule — the 31 labelled assets and 127 antialiased negatives — it takes pixel-art detection from **18/25 to 22/25 with zero false positives**, lowest true positive 0.356 against highest negative 0.186. End to end through `--analyze` over all 155 assets: labelled pixel art 18 → **22**, labelled antialiased **0 → 0**, corpus originals **0 → 0**, and every one of the four flipped verdicts is a labelled pixel-art asset. `references/lessons.md` §28
- **Every hardness measure was reading RGB with the alpha channel thrown away.** In an RGBA source the antialiasing lives in ALPHA; `convert('RGB')` drops it without compositing, so a partially transparent edge pixel keeps its full-strength art colour and the ramp disappears. Measured on a real 512x512 RGBA icon: `plateau_cliff_ratio` **0.320 from raw RGB against 0.000 composited**. This was not theoretical — at v5.4.0 **12 of 119 vector icons (10%)** come back `appears_hard_edged: true` and get `--pixel-art` recommended; all 12 are fixed by measuring on the composite. Hardness is now measured on a composite over the detected background colour; opaque sources take the identical path. §28.5
- **A low `change_line_density` is set aside when `plateau_cliff_ratio` contradicts it.** A density below 0.5 means blocks wider than one pixel, which *entails* plateau-to-plateau edges — so when the cliff ratio says otherwise on a decent sample, the low density is a large simple flat shape, not a pixel grid. Measured on a 512x512 vector icon: density 0.447 (v5.4.0 recommends `--pixel-art`) against cliff 0.070 over 3,737 steps, band ratio 16.079 and blend ratio 2.960. All 18 assets the density rule detects score cliff 1.000, so this costs no detection, and the set-aside evidence is reported rather than dropped. §28.6

Every check is partial-alpha aware: leftover background counts only ESSENTIALLY OPAQUE (alpha ≥ 250) background-coloured pixels, because on an 8-bit output a pale semi-transparent pixel is a recovered fade or an antialiasing ramp — correct output, not leftover. The report carries a `scope_note` saying so.

- ⚠️ **`protected_region_coverage` and leftover-background were both measuring the wrong footprint** until 2026-08-17 — a bounding RECTANGLE contains real background, and counting it made correct output look half-unprotected (gift read 0.874 for a fully protected region; 1.000 once restricted to the enclosed footprint). If you are comparing against numbers recorded before that date, they are not comparable. §21.1
- **`--auto`: TWO PASSES that verify the OUTPUT, not just the source.** ⚠️ Not a loop — there is no iteration construct and no counter. Worst case is two renders and exactly one correction, bounded by the code's shape. Runs `--recommend`, applies its flags (only where you left that option at its default — explicit flags always win, and it prints what it skipped), renders, then RE-MEASURES the written file and re-renders once if the encoded result disagrees with what the pre-encode calibration predicted. Use it when you want the skill to make the call end to end.
- **`--auto-erosion`: `--edge-cleanup-erosion` chosen by measuring the asset against ITSELF.** The fringe metric has no honest global threshold (§18.5), but within one asset every erosion-0 reading is 2–4× its own clean floor, so the calibration reads the answer off that asset's own curve and picks the SMALLEST erosion already at the floor — removing the fringe without eating thin strokes. It independently reproduces both hand-derived defaults: **1** for the GIF path and **0** for WebP/AVIF, the latter because the metric only counts near-opaque pixels and an 8-bit alpha ramp is legitimately pale. In-memory: one erosion pass per candidate, not one render. Full case: §19.
- **Four `--recommend` outputs that were wrong are now right** (full evidence: `references/lessons.md` §18). `--pixel-art` gained a blend-ratio discriminator — ⚠️ **which later measurement showed to be partly a REGRESSION**, see the pixel-art bullet below. `--erosion-exempt-max-size` is suppressed when the transient and design size ranges OVERLAP, because the flag is a size threshold and cannot then separate them — classifying regions correctly is not enough on its own. `--feather-band-multiplier` is only recommended at ≥3.0: below that it narrows the band so far that the antialiasing ramp stops being removed, and the old `max(1.5, …)` clamp was itself producing a fringe (measured 0.2186 at 1.5 vs 0.0000 at the default). Outline-colour verification now retries PER FRAME when the union-across-frames footprint fails, which is what was hiding a real, protectable region behind `candidate_outline_color: null`.
- **Pixel-art detection rebuilt, and scored against a real corpus for the first time.** §18's blend-ratio discriminator rested on the claim that "genuine pixel art has no background-to-art blends by construction" — validated against a synthetic fixture generated in the same session as the theory, which is circular and turned out to be false. Against **37 labelled assets** (25 pixel art, 6 antialiased, plus the 6 vector icons as negatives):

  | rule | correct | pixel art found | false positives |
  |---|---|---|---|
  | v4.0.0 (band ratio AND blend ratio) | 17/37 | 5/25 | 0/12 |
  | + zero-transition-band short-circuit | 19/37 | 7/25 | 0/12 |
  | + **`change_line_density` < 0.5** | **30/37** | **18/25** | **0/12** |

  `change_line_density` counts how often the image changes as you sweep across it — pixel art is drawn on a coarse grid and enlarged, so it changes only at block boundaries. It reads no colour value, so the palette collisions that break the other two measures cannot reach it, and it is scale-free. Below 0.5 is dispositive; a HIGH value proves nothing, so it can only add a hard-edged verdict, never veto one. ⚠️ The 7 remaining misses are all dithered or photographic pixel art. §23
- **`--verify`'s `edge_fringe_check` is now tri-state.** `looks_fringed` is `true` / `false` / **`null`**, with `verdict_basis` giving the reason. The metric is the fraction of the outermost opaque ring closer to the background than to any art colour. It separates cleanly within one asset but the ranges overlap across assets, so a middling value reports INCONCLUSIVE instead of guessing. ⚠️ Never use it to choose `--edge-cleanup-erosion`; compare the asset against its own erosion 0/1/2 outputs, or composite over a dark solid.
- **Frame durations are now read with `im.load()`, not `seek()` alone.** Load-bearing for any non-GIF SOURCE: `GifImagePlugin` populates `info['duration']` during `seek()`, but WebP/AVIF populate it only in `load()`, so seek-only returns the PREVIOUS frame's value. A real 124-frame WebP source came back `[100, 220, 20 ×122]` against a true `[220, 20 ×122, 340]` — one bogus frame prepended, the last one dropped, output 240 ms short — and the readback shared the same flaw, so the script reported "durations preserved exactly." Fixed at all four read sites; the GIF path is byte-identical. Full case: `references/lessons.md` §17.

The default GIF codepath is unchanged — confirmed byte-identical on a real fixture before and after every edit in this round.

## Versioning convention (canonical)

Versioning convention (three-part, `v{major}.{minor}.{correction}` — Harkirat's explicit spec, applies both to this internal version log AND to whatever gets said in the file handed back to him after an edit, so the two never drift):
- **Major** (v2 -> v3): a reviewed, end-to-end-verified round with multiple serious fixes and/or new features/major functionality changes.
- **Minor** (v2 -> v2.1): a single confirmed bug fix in the script itself that doesn't rise to major.
- **Correction / very-minor / note** (v2.2 -> v2.2.1): very, very minor — mainly documentation, but NOT required to be documentation-only (corrected 2026-07-16); a genuinely tiny code tweak, too small to be its own minor bump, fits here too. "Mainly docs" describes the common case, not a hard rule.

All three tiers require the same bar before shipping: confirmed root cause (for a fix) or confirmed-true (for a documentation note), and a real fix/finding, not a guess — the SIZE of the change determines which tier, not the rigor applied. **When deciding which tier a change fits, reason it through explicitly against each tier's actual bar for THIS specific change** — don't pattern-match to whichever tier a similar-sounding past change landed in.

**The version number in this file bumps at "push" (finalize + sync to the live claude.ai skill), not at every repo commit (added 2026-07-16).** A working session can commit several real changes to this file without bumping the number yet — those commits are unreleased work toward the next version. Once each real push gets git-tagged with its version (e.g. `v2.2.1`), `git describe --tags` on any later commit shows exactly how many commits past the last real version you are (e.g. `v2.2.1-3-gabc1234` = 3 unpushed commits past v2.2.1) automatically, with zero manual bookkeeping — no separately maintained counter to keep in sync or forget to reset at push time. At push time, judge the CUMULATIVE tier of everything since the last tag as a whole, not the sum of each commit's own tier, and bump once, to that.

**A live-skill-only session's exported `gif-background-remover-temp-vX.X.X.skill` gets its own provisional version bump**, judged the normal way against whatever that session's edit alone falls under (e.g. a notes-only live-session fix is a correction, temp-version-wise). That provisional number is NOT binding on the repo — it gets reconciled later against the repo's own history, a fresh holistic judgment on what the REPO's actual next version should be given everything accumulated since its last real tag, which may land on a different tier than the temp export used.

**If you are running as the standalone skill on claude.ai, you are in an isolated sandbox and this is the whole picture you get (stated here 2026-08-07 because a session cannot read it anywhere else).** You can read these packaged files — this `SKILL.md`, `references/`, `scripts/` — frozen at whatever version was uploaded. You cannot read the development repo, its `CLAUDE.md`, its git history, or any memory folder, and **you cannot write anything to Harkirat's machine.** So an export does not travel on its own: produce the `gif-background-remover-temp-vX.X.X.skill` file, hand it and the full text of anything you changed to Harkirat in the chat, and he moves it across himself. Don't describe a finding as "saved," "synced," or "logged" — in that context the chat is the only persistence there is.

**"Always hand Harkirat the latest full file" applies specifically to a live-skill-only session (claude.ai, no filesystem) — corrected 2026-07-16.** That convention dates from directly editing the live skill in a single claude.ai chat, where the chat WAS the only persistent copy of the file, so handing over the full text after each edit was the only way he'd have a current copy. In a Claude Code / repo session, the file already persists on disk — there's no need to re-paste the whole thing into chat after every edit; just make the edit and say what changed. Full-file handoff still applies when exporting a live-skill-only session's edits as `gif-background-remover-temp-vX.X.X.skill` (see the temp-drop note above), since that context has no other persistence either. Regardless of context, **keep the actual skill `name` unchanged** in the frontmatter.
